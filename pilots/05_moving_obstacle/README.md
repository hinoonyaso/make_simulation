# Moving obstacle: does the route change?

Single continuous studio scene, 86-second Korean narration and sentence captions, 1920×1080 at 30 fps. The deliverable is intended to make one causal chain visible in the same space: an obstacle is detected, the previous route becomes invalid, the stored plans change, and the TurtleBot3 follows its pose trace.

## Director decisions

- Kept one camera move and one physical set for the full story. The earlier short, chapter-like treatment did not let the viewer watch cause and effect; this scene holds on the same TurtleBot3, obstacle, room, map and goal while their states change.
- Used Blender because the robot/obstacle/map occupy one shared floor plane and their changing spatial relationship is the lesson. No Manim scene is required for this episode.
- Kept the source model's 9 m × 6 m room, two rectangular blocks, start and goal so paths, obstacle, cost field and physical geometry refer to the same coordinates. The studio finish, TurtleBot3 Waffle Pi and orange drum follow `pilots/01_teb_reference`.
- The source trace represents a newly detected circular **person-like obstacle**, not a drum. The drum is a visual stand-in with the same recorded 0.30 m radius. This is disclosed in narration/captions.
- The cost colors are bins of the source's recorded cost values for legibility; cell locations and values come from the source model. They are shown as a floor overlay, not as physical obstacles.

## Data boundary and decision evidence

- `data/trace.json` is generated by `extract_trace.py` from the read-only `topics/08_nav2/output/trace.json`. The script imports `topics/08_nav2/model.py` and calls its `costmap(detected_position)` for the three displayed snapshots (0, 2 and 3 s). It does not run the source simulation or write under `topics/`.
- The exported V9 trace contains those three map/plan states and 172 source playback rows with pose, obstacle truth/detection, command and path ID. The source plans show `initial_plan` at 0 s, `path_invalid` at 2 s, and the next plan at 3 s; source metrics report success at 17.2 s and one path-invalid replan.
- At 2 s the model's first stored replacement plan passes below the detected obstacle; at 3 s the next plan is above the obstacle after its estimated center has moved. The robot pauses at invalidation and its following poses come from the same source trace.
- The model's dynamic object is enabled in the source at 2 s and moves from about y=0.4 m to y=0 m by 2.8 s. The scene time-scales the source playback non-uniformly: it holds the initial pose during the setup, gives the obstacle detection/motion and successive plan snapshots room to read, then plays the remaining source motion toward the goal. Source coordinates and state ordering are unchanged.
- Evidence label: **trace playback** / **educational integrated-model visualization**. This is not a run of ROS 2, Nav2, or Nav2 DWB. The source's own README and `model.py` describe a custom educational stack with synthetic lidar, grid costmap, A* planning, sampled controller and differential-drive kinematics. Do not describe its path choice as a DWB result.

## Pipeline and checks

1. Director authored `visual_manifest.json` as the beat/timing contract.
2. `extract_trace.py` projects the source trace; `core/shared-data/validate_trace.py` validates the V9 result.
3. `blender_scene.py` reads only `data/trace.json` and uses the shared `studio_utils.py`, animation/geometry/material helpers and the kit's TurtleBot3/drum primitives.
4. Narration/caption stages use `core/narration/prepare_audio.py`; assembly and delivery checks use the repository's media pipeline.

The shared kit was not modified. Local kit candidates: a trace-driven, material-binned costmap overlay builder with state visibility keys, and a helper to move all drum components as one assembly. The current scene implements those locally because the kit provides neither behavior. A local attempt to select `FFMPEG` through `scene.render.image_settings.file_format` failed at runtime in Blender 5.2.1 even though the shared `scene_kit.py` template uses that setting. This scene therefore writes PNG frames and encodes them with FFmpeg after Blender exits; the kit was left untouched. Blender also emitted a BlenderMCP “cannot start server in background mode” warning; background renders still completed successfully, so the warning did not affect this pipeline. Candidate for future skill/kit review: explain that a visual prop may stand in for a source obstacle only when geometry and the substitution are both explicitly disclosed. The Director contract was useful for persistent objects and evidence labels; no general Director skill defect was established.

## Revision 02 — review-driven timing correction

The newer explanation review found that the robot was already moving during the plan reveals (old video 47–61 s), while the narration only later said it stops then follows the route. Inspection of `blender_scene.py` confirmed the first stored plan is from source t=2 s, while the concurrent robot playback already advances beyond t=3 s. Sharing a trace had not made these displayed timestamps equal.

`revision_02/visual_manifest.json` keeps one beat contract and records the old encoded source ranges. `revision_02/reedit.py` retimes those ranges to fresh measured narration, preserves their order, and adds short local labels for the stored plan timestamps. The narration identifies the first plan as historical beside later robot playback, and describes the already-moving robot instead of implying a new stop/start at the later beat. It also explains the forbidden-cell color and removes internal source-path jargon from the closing disclaimer. No unrecorded candidate scores or optimum-choice explanations were invented.

Deliverable: `revision_02/output/moving_obstacle_ko_v2.mp4`, 81.93 s, 1920×1080 at 30 fps, AAC narration and 16 sentence cues. The revision remains an educational integrated-model visualization, not Nav2/DWB execution. The existing Blender picture is reused; presentation speed changes by beat, so this is not real-time playback.

Verification: source V9 trace PASS; visual manifest `--require-media` PASS; original scene style PASS; delivery `--require-audio --fps 30 --audio-manifest ... --caption-timing ... --full-decode` PASS. Actual revised encoded frames at 28, 37, 40, 44, 49, 54, 59 and 64 s were sampled; central transition frames and measured caption windows were inspected. Review report: `revision_02/output/review_report.yaml`. Voice performance was not auditioned; inspection covers pixels, measured utterance alignment and audio signal analysis.

With FFmpeg `silencedetect=noise=-45dB:d=0.4`, the longest detected quiet interval dropped from 6.84 s to 1.54 s; intervals longer than 3 s dropped from seven to zero. These are threshold measurements, not subjective listening scores. The original public upload/receipt still refers to the original video.
